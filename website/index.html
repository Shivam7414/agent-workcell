The workcell idea

In a factory, nobody builds a new robot for each job. They take a general-purpose robot and build a workcell around it: fixtures, tooling and safety guarding.

The robot is reused. The cell is engineered.

Are we rebuilding too much of the agent?

Many teams build agents on a raw model API. Each team then writes the same machinery again: intent detection, routing, context management, tool orchestration, multi-step execution and retries.

That path works. A raw API can power a capable autonomous agent, and many good systems are built that way.

The question here is narrower. How much of that machinery is specific to your business?

Keep the agent. Build the rest.

An agent runtime is a program that runs a model in a loop with tools. It is hard to build well, and it is already available. Agent Workcell reuses Claude Code, through the Claude Agent SDK, and treats it as a replaceable part.

What makes an answer right and safe sits around the runtime. It is what the agent knows, what it can touch and what stops it. That part is specific to each business. It is the part this project engineers.

One agent sees the whole question. So the project builds no intent classifier and no router.

This is one approach under test. It is not a verdict on the others. A plain model-API tool loop is planned as a benchmark baseline. No comparison is claimed until that run is recorded.

Claude Code does the agent work

Claude Code runs the model in a loop. It reads the question, calls a tool, reads the result and decides the next step, turn after turn. The project rebuilds none of that.

Claude Code also ships with a shell, file access and the web. Inside the cell, all of it is removed. It keeps the loop and gets five tools.

The options the adapter passes to the Claude Agent SDK
ClaudeAgentOptions(
    tools=[],
    allowed_tools=[PREFIX + name for name in TOOL_NAMES],
    disallowed_tools=list(BUILT_IN_TOOLS),
    permission_mode="dontAsk",
    system_prompt={"type": "file", "path": str(prompt_file)},
    mcp_servers={SERVER_NAME: {"type": "http", "url": request.mcp_url,
                               "headers": {"Authorization": f"Bearer {request.mcp_token}"}}},
    strict_mcp_config=True,
    setting_sources=[],
    cwd=str(workdir),
    max_turns=request.max_turns,
    max_budget_usd=request.max_usd,
    model=request.model,
    env=env,
)
No tools of its own
tools=[] removes them. disallowed_tools names each one again, so one change in the SDK does not open them.
Only the five project tools
permission_mode="dontAsk" denies every other call. Nothing is ever prompted.
Nothing from disk
No settings, MCP servers, CLAUDE.md files or skills are loaded. Each run starts in a new empty folder, deleted afterwards.
No server secrets
Database addresses, passwords and the host key are blanked. The run's own token stays in the MCP headers, out of the model's view.
Bounded
A turn limit and a cost limit for every run. The server adds a time limit.

All four were blocked. A control test that opens the file tool on purpose was caught.

To verify Two checks of the isolated mode need an API key and have not run: no account details reach the model, and no transcript is left behind.

Replaceable The runtime interface is small: start a run, get a stream of events. A scripted runtime already uses it for the tests. Another adapter is added only when there is a real need.

Business meaning, written once and checked

A schema does not say what the data means. The knowledge graph does, in TOML files that people write by hand.

A check compares those files with the live database. It fails when the system changes and the knowledge does not.

What the check catches

  • A table or column that is not described, or no longer exists
  • A stored value with no screen words
  • A link that matches fewer than 95% of the filled rows
  • A calculation whose SQL does not run
  • A rule whose source file or name is gone
  • A generated guide that is stale

The check proves that names are real. It cannot prove that a description is still true.

Where this approach fits

It fits structured business data, where the meaning is small enough to write down and check. The reference knowledge covers 13 tables, 5 calculations and 12 rules.

There is no vector database. Retrieval matches the words of a question against table names, aliases, stored values and screen words. Business questions are full of such names.

Each role gets its own generated guide. It lists only the tables and columns that role can read.

Where retrieval is still needed

Word matching has known limits. A word that is not a name, an alias or a screen word is not found. A bare number does not point to a table.

Large bodies of free text, such as contracts or support tickets, still call for search or embedding retrieval. The project adds that layer only if a benchmark shows word matching is the problem.

To verify Whether word matching is enough. The recorded run is too small to tell.

The model reasons. The database enforces.

The agent writes SQL, and that SQL is always treated as untrusted. No prompt and no SQL parser decides what it may read.

The database decides. Row rules, hidden columns and table access are grants and views, so they apply to every access path.

Identity comes from the server

The host application signs the person in and sends the principal. The server binds it to one database connection. No tool has a user argument, and a test fails if one appears.

Access is grants and views

One security_barrier view per table lists the visible columns and applies the role's row rule. The agent's database role can read those views and nothing else.

One read-only query at a time

Each query runs as a server-side cursor in a read-only transaction, then rolls back. PostgreSQL itself refuses a second statement, SET, COPY and every write.

Every run is bounded

Each query has a time limit, a row cap and a size cap. Each answer has time, cost and turn limits. Each person has daily limits.

Fail closed

A table, column or person the policy does not name gets nothing. guard doctor checks the install at start-up. If it finds an error, the service does not start.

No way out for data

Claude Code's own shell, file and web tools are removed. The server cleans the answer HTML, removes images and shows links as plain text.

What this page does not claim

The guard reduces what a wrong or hostile query can do. It is not proof of security, and its limits are documented.

Read all known limits
  • The project has had no independent security review. Do not use it with production data.
  • The guard is built and tested for PostgreSQL only. MariaDB and MySQL are planned.
  • The agent's role can read the system catalogs: table and column names, view definitions and total row counts. It cannot read row data this way.
  • Query time can depend on the size of the whole table, not only on the rows a person may see.
  • Hostile text in a record can still produce a misleading sentence. Reading other rows or sending data out because of it is a bug.

Measured against the database

Every number on this page comes from a recorded run in the repository. Each run states its date, model, commit, seed and case count.

Where no run exists, the page says so: not measured yet.

  • Gold answers are SQL

    Gold SQL runs through the guard as the same person. It returns what that person may see.

  • Probes test permissions

    A probe reads forbidden values without the guard. The answer, and any file it built, must hold none of them.

  • Graders are plain code

    A number matches only as a whole number: 7 does not match 17. No model grades another model.

  • The runner is a host application

    It asks over the real answer API, so every limit and every tool is the one people use.

  • Cost is capped

    A real run needs a total budget. A scripted runtime checks every case at no cost.

Not measured yet

  • Accuracy. It needs all 28 cases, repeated, with a recorded commit.
  • The gain from reuse. The plain tool-loop baseline is planned, so no comparison exists.
  • Retrieval by word matching. Seven graded answers cannot show whether it is enough.
  • The runtime's isolated mode. Two of its checks need an API key and have not run.

Open source, open to review

The project is at an early stage. The most useful contributions now are a review of the design and attempts to bypass the data guard.

You need Docker, or Python 3.11 or later with a PostgreSQL server.

Start the database, load the data, install the guard
git clone https://github.com/Shivam7414/agent-workcell.git
cd agent-workcell
cp .env.example .env
docker compose up -d db                  # PostgreSQL on 127.0.0.1:54329
docker compose run --rm seed             # the reference ERP: 3,000 purchase orders
docker compose run --rm guard apply      # install the data guard, then check it
Start the answer server and the chat page
pip install -e ".[claude]"
python -m agent_workcell.server          # http://127.0.0.1:8080
python -m reference_erp.host_app         # http://127.0.0.1:8081

Answers call a model and cost money. Sign in with any seeded user and the password workcell-demo.

Run the attack suite against a test database
export ERP_TEST_DATABASE_URL=postgresql://erp_owner:erp_owner_dev@127.0.0.1:54329/erp_test
pytest -m db

The suite runs hostile queries as six test people. Each result must equal the result on a schema that holds only that person's rows.

A new bypass idea is welcome as a test case, even one that already fails. Report a real problem in private, through the repository's security advisories.

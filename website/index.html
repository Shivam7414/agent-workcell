Reuse the agent. Engineer the environment.

Do not build a custom agent, and do not tune a retrieval pipeline for every question type. Agent Workcell reuses Claude Code as its agent runtime and engineers the environment it works in: business data and documents, behind one data guard.

The workcell idea

In a factory, nobody builds a new robot for every job. They reuse a general-purpose robot and engineer the workcell around it: fixtures, tools and safety guarding. Agent Workcell applies the same idea to knowledge work.

The agent is reused. The environment is engineered.

  1. The robot Claude CodeAn existing agent runtime, reused as it is
  2. Fixtures Knowledge graphChecked against the live database
  3. Tooling Seven tools over MCPRead knowledge, data and documents; make files
  4. Safety guarding Data guardThe database decides access

  6. Acceptance tests EvaluationCases graded against the database

Why tune a pipeline for every question?

A conventional retrieval pipeline defines how context is found: chunking, embeddings, vector search, top-k selection and reranking. A router may send different question types through different paths, each with its own retrieval rules.

Each stage needs tuning. A prompt tweak or retrieval change that helps one question type can hurt another, so previously working questions need regression testing as the system evolves. These pipelines can work well; search and retrieval remain useful, especially for large collections of unstructured text.

Engineer the environment, not a path for every question.

Claude Code provides a capable agent loop: it reads context, chooses tools, observes results and decides what to do next. Building and maintaining a custom agent duplicates that work. Agent Workcell reuses the runtime instead of building a separate orchestration loop.

The project engineers the environment the agent can explore: checked business knowledge, documents, seven tools over MCP and database-enforced access. The same agent and tool set handle different question types; the agent chooses which knowledge, data or documents to inspect, without a question-type router.

This is an approach under test, not a verdict on other designs. No controlled comparison with a retrieval pipeline or a plain tool loop has been run.

Three questions, two approaches

A predefined retrieval pipeline selects context through configured steps. In Agent Workcell, the agent decides which available knowledge or data to inspect, which tool to use and whether another step is needed.

What retrieval still exists?

Not used for business data

  • Embeddings
  • Vector search

Used

  • Whole role guide in every promptIt fits this 13-table reference schema; a large schema may need a different approach.
  • Keyword lookup: knowledgeJoin paths are defined in code; this is still a retrieval mechanism, not unrestricted exploration.
  • SQL written by the agentThe database executes the query, but correctness still depends on the agent choosing the right tables, joins, filters and calculations.
  • Document search: search_documentsPassages, embeddings and hybrid search for free text, as a tool the agent calls when it decides to, through the same guard.

Claude Code does the agent work

Claude Code runs the agent loop: it chooses a tool, reads the result and decides whether to continue, change direction or answer. Agent Workcell reuses that loop rather than rebuilding it.

Its own shell, file and web tools are removed. It keeps the loop and gets seven project tools.

The options the adapter passes to the Claude Agent SDK
ClaudeAgentOptions(

    allowed_tools=[PREFIX + name for name in TOOL_NAMES],

    permission_mode="dontAsk",
    system_prompt={"type": "file", "path": str(prompt_file)},
    mcp_servers={SERVER_NAME: {"type": "http", "url": request.mcp_url,
                               "headers": {"Authorization": f"Bearer {request.mcp_token}"}}},
    strict_mcp_config=True,
    setting_sources=[],
    cwd=str(workdir),
    max_turns=request.max_turns,
    max_budget_usd=request.max_usd,
    model=request.model,
    env=env,
)
No built-in tools
tools=[] removes them; disallowed_tools blocks each one again.
Only project tools
dontAsk denies every other call, without a prompt.
Nothing from disk
No settings, MCP servers, CLAUDE.md or skills. Each person gets their own folder, which holds only that person's sessions.
No server secrets
Database credentials and the host key are removed from its environment. The run token stays in the MCP headers.
Bounded
Turn and cost limits per run, plus a server time limit.
API key only
Products may not run on a claude.ai sign-in. The sign-in mode is a local trial: 127.0.0.1, one answer at a time.
One process per answer
Each answer starts a Claude Code CLI process (Node.js). Plan CPU, memory and API cost for it.

Business meaning, written once and checked

A schema does not say what the data means. The knowledge graph does, in hand-written TOML files.

A check fails when the database changes and the knowledge does not.

The check fails on

  • A table or column not described, or gone
  • A stored value with no screen words
  • A link that matches under 95% of filled rows
  • A calculation whose SQL does not run
  • A rule whose source file or name is gone
  • A stale generated guide

It proves names are real, not that descriptions are true.

The model reasons. The database enforces.

The agent's SQL is always untrusted. No prompt and no SQL parser decides what it may read.

Row rules, hidden columns and table access are database grants and views. They apply to every access path.

Identity comes from the server

The host application sends the principal; the server binds it to one connection. No tool takes a user argument.

Access is grants and views

One security_barrier view per table applies the role's row rule. The agent role can read only these views.

One read-only query at a time

A server-side cursor in a read-only transaction. PostgreSQL refuses a second statement, SET, COPY and writes.

Every run is bounded

Limits per query, per answer and per person per day.

Fail closed

Anything the policy does not name gets nothing. If guard doctor finds an error, the service does not start.

Restricted tools, bounded data access

No shell, file or web tools. The answer HTML is cleaned, with no images and no live links.

What this page does not claim

The guard limits what a wrong or hostile query can do. It is not proof of security.

Read all known limits
  • The project has had no independent security review. Do not use it with production data.
  • The guard is built and tested for PostgreSQL only. MariaDB and MySQL are planned.
  • The agent role can read the system catalogs: names, view definitions and row counts, but no row data.
  • Query time can reflect the whole table, not only the visible rows.
  • Hostile text in a record can still mislead an answer. If it widens access or sends data out, that is a bug.

Documents, in the same cell

Agreements, policies, certificates and files attached to an order use the same flow as business data. They live in the same database, behind the same guard, and the same agent decides when to look them up.

Search over free text is useful, so the cell offers it as two tools. It is not a pipeline in front of every question: Claude Code chooses when to search, what for, and whether to read more.

Same database, same guard

Documents, versions, passages and embeddings are tables in the policy. A supplier user finds only documents shared with their supplier; internal evaluations stay with the company.

Words and meaning

Hybrid search: PostgreSQL full-text search and pgvector embeddings from OpenAI or OpenRouter, chosen in settings. It runs on the person's guarded connection.

Read, compare, cite

read_document reads passages in order, a whole version, or two versions to compare. Each passage carries its document number, version and page or section.

Sources from the server

Each answer that used documents ends with a sources list built from the database rows, so the host can show evidence without trusting the model's text.

Text from documents is data

Passages reach the model escaped, inside their own block. A document the person may not read looks exactly like one that does not exist.

Upload and processing

The host uploads a file; a worker reads it into passages in plain code, with retries and a status for each version. Its database role can add passages and nothing more.

Within these limits

The design and its known limits are in the architecture's "Documents" section.

Read the design
  • Text, Markdown and CSV files are read. Other file types are refused at upload.
  • Search compares every candidate passage exactly. Its speed on a large document set is not measured.
  • Answer quality on document questions is not measured: no recorded run covers documents.
  • A source is marked as cited when the answer names its document number. The page or wording the answer attributes to it is not checked.

Open problems

Reusing an agent runtime moves work out of the project, but it does not remove every problem. These are the ones this approach has not solved, stated so that nobody adopts it on a wrong assumption.

Each carries its status: not solved, planned, not measured or trade-off. What is not measured about answers is listed under Evaluation.

Not solved

One Claude Code process per answer

Each answer starts its own Claude Code CLI process (Node.js), in the person's own folder, with its own tool token. Follow-up questions resume the person's own session. This keeps people apart: no session or token is shared, so one person's conversation cannot reach another person's answer. The price is a new process for every answer, with its start-up time, memory and CPU. How much each process needs is not measured.

Planned

No limit across the whole server

Answers running at once are limited per person, two by default, but not across all people. Many people asking at the same moment start as many processes, and can use up the host's memory and CPU.

Not solved

Several servers do not share limits

Running answers are counted inside one server process. Behind a load balancer, each process counts its own. Daily limits hold only if the processes share one audit file.

Not solved

Hostile text can still mislead

Text in a record or a document can contain instructions. The design stops it from widening access or sending data out, but it can still lead the model to a misleading sentence in an answer.

Trade-off

Depending on Claude Code

Reusing Claude Code means the project does not control the runtime. It changes between versions, so the protection rests on its configuration and a pinned version, checked by hand after each change. A product runs on a paid API key; the Claude Code sign-in is for a local trial only.

Not measured

Documents at scale

Search compares every candidate passage exactly, and its speed on a large document set is not measured. Only text, Markdown and CSV files are read. A source counts as cited when the answer names its document number; the page or wording is not checked.

Planned

One database engine, no outside review

The data guard is built and tested for PostgreSQL only; MariaDB and MySQL are planned. The project has had no independent security review. Do not use it with production data.

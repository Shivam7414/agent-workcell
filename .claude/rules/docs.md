# Documentation

Readers are outside developers who have never seen this project.

- Professional, plain English. Short sentences. No slang, jokes or casual phrasing. Explain a term the first time it
  appears.
- Say what exists and what does not. Planned parts are marked **planned**. Unproven design choices are marked
  **to verify**. Keep `docs/roadmap.md` true.
- No numbers without a recorded run (`bench/results/`). No "first", "best", "revolutionary" or similar.
- No real company, client, deployment or person. Examples use the reference ERP.
- Give the reason and the cost of each design choice, not only the choice.
- A limit we know about goes in the docs ("Known limits"), not only in an issue.
- When code changes behaviour that a doc describes, change the doc in the same step.
